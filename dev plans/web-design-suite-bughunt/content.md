# Bug hunt: content-model-to-ui, component-state-matrix, figma-variables-sync

Environment: Windows 11, Python 3.14.5 (cp1252 locale when `PYTHONIOENCODING`
unset), Node 26. Plugin copied to a workdir and run from each skill's own
folder as documented. Fixtures: a realistic Supabase-style schema (enums, FKs,
many-to-many join table, arrays, jsonb, RLS/comments, CHECKs); a 2-component
state matrix (button/badge) with tokens+base+templates; a REST-shaped Figma
variables export (3 tiers, cross-collection alias chain, broken alias, alias
cycle, alpha color, hidden/remote flags) plus plugin/dtcg/records-shape
variants.

## Bugs

**CONT-1** · wrong-result · `content-model-to-ui/scripts/introspect_schema.py:663` · An inline CHECK containing the substring "not null" (e.g. `CHECK (col IS NOT NULL OR status = 'draft')`) flips a genuinely-nullable column to `nullable=false`, because `col.nullable = "not null" not in low` is a plain substring test over the whole modifier text, not just a top-level `NOT NULL` keyword.
Repro (from `content-model-to-ui`): DDL with `published_at timestamptz CHECK (published_at IS NOT NULL OR status = 'draft')` (no top-level `NOT NULL`); `python -m scripts.introspect_schema schema.sql -o model.json`, inspect `products.published_at`.
Observed: `"nullable": false` plus a spurious validation rule `{"rule":"required","source":"NOT NULL with no DEFAULT","message":"Published At is required."}`. Expected: nullable true, no required rule — the schema only requires it conditionally.
Fix: reuse the existing word-boundary modifier-keyword scan to detect a top-level `NOT NULL`, instead of a substring search over text that includes CHECK expressions. Confidence: high.

**CONT-2** · wrong-result · `content-model-to-ui/scripts/introspect_schema.py:1157-1171` · A one-to-many relationship's `control` is set to `"inline-subtable"` from `ON DELETE CASCADE` alone, ignoring whether the child has a title of its own — contradicting SKILL.md ("Owned children (ON DELETE CASCADE, **no title of their own**) live inside the parent's form"). The correct "no title" test already exists (for `screens.primary_home`) but is never applied to the relationship's `control`.
Repro: `organizations`(pk) `users`(organization_id uuid NOT NULL REFERENCES organizations(id) ON DELETE CASCADE, full_name text, email text, ...). From `content-model-to-ui`: `python -m scripts.introspect_schema schema.sql -o model.json --summary`, then `python -m scripts.scaffold_ui model.json --out out` and read `features/organizations/OrganizationDetail.tsx`.
Observed: summary shows `rel one-to-many -> users [inline-subtable]`; generated `OrganizationDetail.tsx` contains `{/* TODO(inline-subtable): one-to-many to \`users\`. ... belong inside the parent's own form */}` even though `users` plainly has its own identity (`full_name`, `email`). Same happens for every cascade-deleted child in the fixture (`categories`, `products`, `orders`) — i.e. every table in a typical multi-tenant schema.
Fix: gate the `owned`/control choice on the same "no textual non-FK column" test used for `primary_home`. Confidence: high.

**CONT-3** · broken-doc · `content-model-to-ui/scripts/scaffold_ui.py:380` (template; lands in generated `ui/Button/Button.module.css`) · The default `--stack css-modules` scaffold's own Button component hardcodes `animation-duration: var(--dur-slower)` inside `@media (prefers-reduced-motion: reduce)`. The comment directly above it talks about needing a `design-audit-ignore-next-line` pragma for this exact known gap but never adds one, so `audit_design.py --strict` — the literal Step-6 command in SKILL.md — fails on every fresh scaffold, contradicting "the scaffold is built to exit clean on a fresh run and does."
Repro: (content-model-to-ui) `python -m scripts.scaffold_ui model.json --out out-css` (default stack); (web-design-studio) `python -m scripts.audit_design out-css --strict`.
Observed: `ui/Button/Button.module.css:120 warn L6 tier1-motion ... Component code reads \`--dur-slower\` directly ... 0 error(s), 1 warning(s)`, exit 1. `--stack tailwind` output audits clean (exit 0) — the bug is css-modules-only (tailwind never emits `Button.module.css`).
Fix: add the pragma the neighboring comment describes, or route through a `--motion-*` pair. Confidence: high.

**CONT-4** · wrong-result · `content-model-to-ui/scripts/scaffold_ui.py:618` (`CONTROL_TSX` template) · The shared `ui/Control.tsx` primitives (`TextInput`/`NumberInput`/`TextArea`/`Select`) generated in every scaffold, both stacks, fail a11y-audit-runner's `a11y_static.py` with 4 hard `control-no-label` errors (SC 3.3.2/4.1.2) — unconditionally, with no ignore pragma — even though the real per-entity forms (e.g. `ProductForm.tsx`) correctly wire `id`/`<Field>`/`<label>` together and are themselves clean.
Repro: (a11y-audit-runner) `python -m scripts.a11y_static out-css/ui/Control` (and `out-tw/ui/Control`).
Observed: `<input type="text"> has no label...`, `<input type="number">...`, `<textarea>...`, `<select>...` — 4 errors, exit 1, regardless of `--strict`.
Fix: add an `a11y-audit-ignore-file` pragma (the suite's own documented mechanism, used nowhere in the generator) to this generic, prop-spreading primitives file, noting real forms supply the label via `Field`. Confidence: high (the false-positive nature of the underlying check is plausible, but the suite controls both the generator and the auditor and ships neither a pragma nor a doc note reconciling them).

**CSM-1** · wrong-result · `component-state-matrix/scripts/generate_matrix.py:521` · SKILL.md: "`{attrs}` is mandatory in a template... Without it, state, variant and size cannot be applied and every cell renders identically — the generator refuses." The actual guard is `if "{content}" not in tpl and "{attrs}" not in tpl:` — it only refuses when **both** placeholders are missing, so a template with `{content}` but no `{attrs}` is silently accepted.
Repro (from `component-state-matrix`): manifest with `"template": "<span class=\"badge\">{content}</span>"` (7 states, 2 variants declared) and `python -m scripts.generate_matrix matrix.json --out out.html`.
Observed: exit 0, "state coverage: every declared state has a matching rule"; every rendered cell is byte-identical (`grep -o '<span class="badge">[^<]*</span>' out.html | sort -u` returns exactly 1 line) — state/variant/size are silently never applied, which is precisely the failure the doc says is refused, and the coverage line actively misreports it as fine.
Fix: `if "{attrs}" not in tpl:` should refuse on its own (optionally with the `{content}`-too check kept as a second, distinct message). Confidence: high.

**FIGMA-1** · wrong-result · `figma-variables-sync/scripts/figma_to_tokens.py:541` (`parse_records`) · The documented "records" shape ("a flat list of `{name, type, value}` records") never merges rows sharing `(collection, name)` across different `mode`s into one variable, unlike `parse_plugin`'s `_ingest`, which does the equivalent merge correctly. Each mode becomes an independent single-mode variable, and the "which mode counts as this variable's default" fallback in `Converter.blocks()` then routes **every** such fragment to `:root`.
Repro (from `figma-variables-sync`): a records-shape JSON list with two rows both named `bg/surface`, same collection, `"mode":"Light"` aliasing one primitive and `"mode":"Dark"` aliasing another; `python -m scripts.figma_to_tokens records.json --format css`.
Observed: `:root { ... --bg-surface: var(--neutral-0); --bg-surface: var(--neutral-900); }` — both under `:root`, no `[data-theme="dark"]` block at all. CSS cascade means the Dark value silently wins for every theme. No warning, exit 0. The identical logical input via the "plugin" shape correctly produces `:root {--bg-surface: var(--neutral-0);}` + `[data-theme="dark"]{--bg-surface: var(--neutral-900);}`.
Fix: merge rows in `parse_records` by `(collection, name)` before appending to `doc.variables`, the same way `parse_plugin` does. Confidence: high.

**FIGMA-2** · crash · `figma-variables-sync/scripts/figma_audit.py:1443`, raised from `main()` at `:1507` · `--format markdown`'s footer contains "ΔE<sub>OK</sub>" (Greek Δ, U+0394), which is not representable in cp1252. On a plain Windows console/CI without `PYTHONIOENCODING=utf-8` this is an actual uncaught crash.
Repro (from `figma-variables-sync`), PowerShell with `$env:PYTHONIOENCODING=$null`: `python -m scripts.figma_audit export.json --format markdown`.
Observed: `UnicodeEncodeError: 'charmap' codec can't encode character 'Δ' in position 3674: character maps to <undefined>`, full traceback to stderr, exit 1 via unhandled exception (not the documented 0/1/2 contract). `--format report` and `--format json` on the same file under the same conditions do **not** crash.
Fix: avoid the non-cp1252 character in the emitted footer, or make stdout UTF-8-safe (`errors="replace"` or reconfigure) before printing. Confidence: high — actually triggered, not just present in source.

**FIGMA-3** · wrong-result · `figma-variables-sync/scripts/figma_to_tokens.py:121` · `--reverse` hardcodes `COMPOSITE_ONLY |= {"text-5xl", "text-6xl", "font-sans", "font-mono"}`. `font-sans`/`font-mono` are plain STRING font-stacks, not composites — they are listed in `references/figma-mapping.md` §4 as STRING "Maps cleanly to ... `--font-sans`, `--font-mono`" and registered as ordinary TIER1 primitives (`token-contract.md`). The comment above the set talks about "a CSS shorthand (`font` shorthand)... or a clamp()", which fits `text-5xl`/`text-6xl` (documented `clamp()`s) but not a font stack.
Repro (from `figma-variables-sync`): tokens.json (as produced by this same script) containing `--font-sans: Inter, sans-serif` with no alias/clamp/shadow involved; `python -m scripts.figma_to_tokens tokens.json --reverse`.
Observed: `composite (1): --font-sans is a composite (a CSS shorthand, a shadow pair or a clamp)... Dropped from the payload`, exit 1; `--font-sans`/`--font-mono` can never be sent back to Figma via `--reverse`, for any project.
Fix: remove `font-sans`/`font-mono` from `COMPOSITE_ONLY`. Confidence: high.

**FIGMA-4** · wrong-result · `figma-variables-sync/scripts/figma_audit.py:1162-1180` (`check_dark_mode`) · `MISSING_DARK_MODE`'s "3+ semantic colour roles" count only recognises `bg-*`/`fg-*`-style slugs (`BG_ROLE_RE`/`TEXT_ROLE_RE`, `figma_audit.py:777-778`); a single-mode "Semantic"-named collection made entirely of e.g. `border-*` roles never trips the check no matter how many it has.
Repro (from `figma-variables-sync`): plugin-shape export, one collection named "Semantic", one mode, 3 COLOR vars `border/default`, `border/strong`, `border/subtle`; `python -m scripts.figma_audit export.json --fail-on never`. Then swap 2 of the 3 names to `bg/...`/`fg/...` and re-run.
Observed: no `MISSING_DARK_MODE` finding at any border-only count; confirmed the check fires correctly once >= 3 vars are named `bg-*`/`fg-*` instead (`` `Semantic` holds 3 semantic colour roles and one mode ``).
Fix: broaden the role-name test to cover other semantic-color prefixes (border/icon/link/etc.), or count any COLOR var in a collection whose own name reads as semantic. Confidence: medium.
