# Bug hunt: a11y-audit-runner / perf-budget-gate / email-template-system

## Bugs

**GATE-1** · wrong-result (false positive) · `a11y-audit-runner/scripts/a11y_static.py:427-430` (`scan_tags`, JSX spread), consumed by `_labelled()` (`:1253-1270`), `_has_name()` (`:1273-1291`), and the `<img>` alt check (`:880-896`) · A JSX spread attribute (`{...props}`) is recorded only under a private `"\x00spread"` key that no rule ever reads, so an element that spreads its accessible-name props is scored exactly like an element with **no attributes at all** — the opposite of the documented "`{dynamicValue}` is present but unknowable" policy. · Repro, from `a11y-audit-runner` folder: `python -m scripts.a11y_static widget.jsx` where `widget.jsx` contains `<input {...inputProps} />`, `<img {...inputProps} />`, `<button {...inputProps} />` inside one component. · Observed: `13 error F control-no-label`, `15 error N img-no-alt`, `17 error N empty-control` for the three spread elements — while `<img alt={altText} />` and `<button>{label}</button>` (named JSX-expression attrs, tested in the same file) correctly produce **no** finding. · Expected: spread props treated the same as any other unknowable dynamic value — no finding, per SKILL.md line 128 ("a `{dynamicValue}` attribute is treated as present but unknowable... a false positive on a runtime value is how a linter gets switched off"). This will false-positive on essentially every design-system wrapper component that forwards `aria-*`/`alt` via spread. · Fix: when `"\x00spread"` is in `attrs`, short-circuit the label/name/alt checks for that element (treat as unknowable) instead of falling through to "no mechanism found". · Confidence: high.

**GATE-2** · crash · `a11y-audit-runner/scripts/a11y_static.py:1210-1211` (heading-skip message) & `:1675` (stdout write); `perf-budget-gate/scripts/perf_audit.py:896-897` (animated-layout-prop fix text) & `:1692` (stdout write) · Both scripts' own hardcoded finding text uses the arrow glyph `→` (U+2192), which does not exist in the Windows default code page (cp1252). With no `PYTHONIOENCODING` set — i.e. a real terminal, a git pre-commit hook, or plain CI — the default text report crashes instead of printing. · Repro 1, from `a11y-audit-runner` folder: `Remove-Item Env:\PYTHONIOENCODING -ErrorAction SilentlyContinue; python -m scripts.a11y_static bad.html` where `bad.html` has an `h1` immediately followed by an `h3`. Repro 2, from `perf-budget-gate` folder: same env, `python -m scripts.perf_audit dist/` where `dist/` has a CSS rule with `transition-property: width, top;`. · Observed (both): `UnicodeEncodeError: 'charmap' codec can't encode character '→' ... character maps to <undefined>` and a full Python traceback on stderr; no report is produced at all. `--quiet` does not help (the arrow is in the finding `message`, not the `fix` text `--quiet` suppresses); `--json` is unaffected (`json.dumps` escapes non-ASCII by default). · Expected: the documented text report, exit 0/1. · Fix: `sys.stdout.reconfigure(encoding=sys.stdout.encoding, errors="backslashreplace")` (or `"replace"`) at the top of `main()`, or replace `→` with `->` in the literal strings. · Confidence: high — this is a specific, triggered instance of the already-known "13 scripts contain non-cp1252 characters" issue, reported per the hunt instructions because it was actually reproduced, with exact files/commands.

**GATE-3** · wrong-result/cosmetic · `a11y-audit-runner/scripts/a11y_runtime.mjs:451` (`summary: (n.failureSummary||'').replace(/\s+/g,' ').trim().slice(0,300)`) and `:479` (`` `${v.nodes[0]?v.nodes[0].summary:''} ${v.helpUrl}`.trim() ``) · axe's `failureSummary` is hard-truncated at exactly 300 characters with no word-boundary check or ellipsis, then glued straight onto the rule's `helpUrl` with one space. Any axe rule whose summary exceeds 300 chars (common — "Fix any/all of the following:" lists) prints a sentence that stops mid-word and runs into the URL. · Repro, from `a11y-audit-runner/scripts` with `NODE_PATH` pointing at a `node_modules` containing `playwright`+`axe-core`: `node a11y_runtime.mjs --url http://127.0.0.1:8091/bad.html --browser <chromium>` against a page with an unlabelled `<button>`/`<img>`/`<input>` (axe rules `button-name`, `image-alt`, `label`). · Observed (quoted verbatim from output): `Element has no title attribute Element do` then, on the very next line, `https://dequeuniversity.com/rules/axe/4.13/button-name?application=axeAPI` — "Element do" is not a word; `image-alt`'s fix similarly ends "...semantics were not o". · Expected: full fix text, or a truncation that ends on a word with `…`, kept separate from the URL. · Fix: trim to the last whitespace before 300 chars and append `…`; put `helpUrl` on its own report line (it already has its own `L.push` slot available). · Confidence: high.

**GATE-4** · crash · `email-template-system/scripts/build_email.py:894` (`ENTITIES` table: `"&larr;": "←", "&rarr;": "→"`) feeding `generate_text()`, and `:1196` (`sys.stdout.write(text)` in the `--text-only` branch) · `--text-only` with no `--out` crashes with the same cp1252 `UnicodeEncodeError` as GATE-2 whenever the source template contains the very common `&rarr;`/`&larr;` entities (e.g. a "Shop now &rarr;" call-to-action), because `unescape_entities()` turns them into real arrow characters before they hit stdout. · Repro, from `email-template-system` folder, no `PYTHONIOENCODING` set: `python -m scripts.build_email arrow-test.html --tokens assets\email-tokens.json --text-only`, where `arrow-test.html`'s body is `<p>Shop the new collection &rarr; today.</p>`. · Observed: `UnicodeEncodeError: 'charmap' codec can't encode character '→' in position 24: character maps to <undefined>`; exit 1 (traceback), no text produced. Control check: the same file compiled WITHOUT `--text-only` (normal HTML output) does **not** crash, because entities are left un-decoded in HTML — this is specific to the plain-text/stdout path. `--text FILE` is also safe (explicit `encoding="utf-8"` file write). · Expected: the plain-text alternative printed to stdout, exit 0, per `email-workflow.md` §2 ("`--text-only` — to read the text part before shipping it"). · Fix: same as GATE-2, reconfigure stdout or write bytes explicitly as UTF-8. · Confidence: high.

**GATE-5** · portability · `perf-budget-gate/scripts/measure_vitals.mjs:499-506` (`loadLabBudget`, `JSON.parse(fs.readFileSync(file,'utf8'))` at `:504`) and `a11y-audit-runner/scripts/a11y_runtime.mjs:1551-1556` (`loadBudget`) · Neither strips a leading UTF-8 BOM before `JSON.parse`. A budget/keymap file saved with a BOM — which is exactly what Notepad and PowerShell's own `Out-File -Encoding utf8` / `Set-Content -Encoding utf8` write by default on Windows — fails to parse, while byte-identical content without a BOM works. · Repro, from `perf-budget-gate\scripts` folder: `'{ "defaults": { "lab": { "lcp_ms": 1 } } }' | Out-File -Encoding utf8 tiny-budget.json` then `node measure_vitals.mjs http://127.0.0.1:8092/index.html --browser <chromium> --budget tiny-budget.json`. · Observed: `measure_vitals: cannot parse ...tiny-budget.json: Unexpected token 'ï»¿', "ï»¿{ "defaul"... is not valid JSON`, exit 2 (bad invocation) — even though the JSON is valid. Rewriting the identical text with `[System.IO.File]::WriteAllText(path, text, (New-Object System.Text.UTF8Encoding $false))` (no BOM) then correctly reports `Budget breaches: LCP 600 > 1`, exit 1. The same BOM'd file reproduces the identical `Unexpected token 'ï»¿'` failure against `a11y_runtime.mjs --budget`. · Expected: a BOM is a normal, standards-legal way to write UTF-8 and should be ignored, as Python's own `json.loads` at least names it explicitly ("Unexpected UTF-8 BOM") in the sibling Python scripts' budget loaders. · Fix: strip a leading UTF-8 BOM (the single `U+FEFF` code point) from the file text before `JSON.parse` in both scripts. · Confidence: high.

**GATE-6** · wrong-result (edge case) · `email-template-system/scripts/lint_email.py:241-245` (`is_preheader()`) vs `:500-508` (the preheader-detection loop inside `check_head()`) · `is_preheader()` treats a hidden block as a preheader when it has `display:none` plus **either** `max-height:0` **or** `opacity:0`, but the separate detection loop that decides whether to raise the `no preheader found` error only checks `display:none` + `max-height:0` (no `opacity:0` fallback, and it is checked only when `data-preheader` is absent). A hand-authored template that hides its preheader with `display:none;opacity:0` and no `data-preheader` attribute would be wrongly flagged as having no preheader at all. Does not reproduce against the suite's own 3 shipped templates because all three use `data-preheader="1"`, which the same loop checks first and short-circuits on. · Fix: reuse `is_preheader()` inside `check_head()`'s loop instead of re-implementing a narrower version of the same test. · Confidence: medium (confirmed by reading; not observed as a false positive on any real/shipped content, only on a constructed edge case).
