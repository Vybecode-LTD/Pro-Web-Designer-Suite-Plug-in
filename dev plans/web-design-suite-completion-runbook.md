# Pro Web Design Suite: the completion runbook

**Written 2026-10-28** from [the full audit of `main` at `8441ff0`](web-design-suite-audit-2026-10-28.md). It says what "100% done" means for this plugin, where it stands against that, and then every step that gets it there: every one of the audit's 281 findings and its 23 open items is assigned to a numbered work package below, in order, with its files, its tests and its done-check. Nothing is left to be remembered.

**How to use it.** A session takes the next package in order (§4), does it by the per-PR protocol (§5), and ticks it in the status table (§7). The owner's decisions (§2) are asked once, at the start, and recorded here. The audit's finding ids (`PY-B-1`, `JS-B-1`, …) point into [`web-design-suite-audit-2026-10-28/`](web-design-suite-audit-2026-10-28/), where each has its file, line, evidence and proposed fix; the open-item ids (`L1` to `L23`) point into `plan-what-is-left.md` there. The plan's conventions hold: each package gets an N-item in the completion plan and a P-row in the execution plan before its PR (next free: **N60** and **P66**), and `check_execution_plan.py` must read 0 open at the end of each session.

## 4. The work, in order

Twenty-four packages in eight stages. Each row: the package, what it closes, the files, the tests it must carry, its size (S under a session's quarter, M a half, L a session), and what it waits for. **The order is by risk and dependency, not by severity alone:** stage 0 makes the next merges trustworthy, stage 1 stops the scripts hurting users' files, stage 2 stops the gates lying, and the rest follows by file cluster so no file is read twice (the plan's efficiency rule 4).

Every package that changes code carries, for every finding it closes, a regression test seen failing on `v4.0.1` (`python -B tools/fail_before.py TEST_IDS`, after P68 separates errors from failures) and passing on the branch, and its CHANGELOG entry names the tests. Every package that changes `shared/project_config.py`, `shared/dtcg.py` or `shared/project_config.mjs` copies the master over every copy before the push. A package over 100 files splits.

## 5. The per-PR protocol

Unchanged from the execution plan's §6, with the audit's additions in bold.

1. **Before the branch:** the N-item in the completion plan and the P-row in the execution plan; `check_execution_plan.py` green. **Look at the CPU before a long run.**
2. **The branch:** one per PR, from `main`, named `fix/p<nn>-<slug>` or `docs/p<nn>-<slug>`; up to three stacked when they share files, merged bottom-up.
3. **The work:** the fix, then **for each finding id the regression test, run through `fail_before.py` against `v4.0.1`** (the default REV) and recorded in the CHANGELOG entry as "Regression tests: `test_x.Class.test_y`, which fail on 4.0.1"; **the fail-before table pasted into the PR body, with the errors column empty**. A gate change goes into `design-rules.json` first and `sync_rules.py` regenerates. The shared masters copied over every copy. Docs updated at the point of change, in the same PR.
4. **Before the push:** `python -B tools/check.py` green (it now selects by the folder map); the staged diff read for secrets; under 100 files; the PR number predicted (the highest plus one; today #215).
5. **The push:** once, when the work is done; fixes batched after; never a push to see CI. Auto-fix on for the PR.
6. **The merge:** by Claude, when CI is green on the head (the ruleset now requires it), every thread is answered and resolved, GitHub reports it clean; a merge commit, `--match-head-commit` with the full SHA. CodeRabbit and Codex are not gates; their real findings are fixed.
7. **After the merge:** the status row in §7 ticked with the PR number; the session's docs at the end of the session, in their own PR.

**Session rules that still bind:** one session at a time per project, in the main checkout; up to 750K tokens with no compacting, usage reported after each PR and the handoff written well before the cap; the handoff and the 4 KB starting prompt at every session's end, with the chip and the printed prompt; never grep `tooling/`; never write into OneDrive; `python -B`; the four old ids stay; nothing commits to the distribution repository by hand; nobody submits, publishes or withdraws in the portal but the owner.
