# Claude Code capabilities for plugin authors

This is a reference for the web-design-suite review. It was researched on 2026-09-23 from the live docs at code.claude.com and from the local CLI (`claude.exe` 2.1.280): I read `plugin eval --help` and ran `plugin eval init --bare` in a scratch copy. Every fact links to its source. Anything marked *(inference)* is my own reading, not something the docs state.

## 1. `claude plugin eval`

- **Requirements.** Claude Code v2.1.269 or later; the local 2.1.280 qualifies. Every agent run and every judge call is a real model call that counts against the account ([evals#requirements](https://code.claude.com/docs/en/plugin-evals#requirements)).
- **How a run works.** Each case runs in a fresh, isolated `claude -p` session with only the plugin loaded, 3 times by default. By default it also runs the same number of times with no plugin ([evals#how-an-eval-run-works](https://code.claude.com/docs/en/plugin-evals#how-an-eval-run-works)).
- **Layout.** A case is any directory under the eval dir that contains `prompt.md`, `case.yaml`, or both. To group cases, nest them under a directory that isn't itself a case. Runs write `results/<timestamp>/`, which belongs in `.gitignore` ([evals#write-and-refine-cases](https://code.claude.com/docs/en/plugin-evals#write-and-refine-cases)).
- **`prompt.md` plus `graders/*.md`.** This is what `init` writes and what the docs recommend for new suites. The body is sent verbatim as the prompt (`@path` is not expanded). Frontmatter keys, with defaults in brackets; an unknown key is an error: `schema_version` ("1.1", automatic), `name` (directory name), `description`, `tags`, `plugins` (nearest enclosing plugin; e.g. `["../.."]`), `runs` (3, range 1–50), `expected_outcome`, `model`, `max_turns` (10, max 200), `timeout_seconds` (300, max 3600), `allowed_tools` (`[]`), `append_system_prompt`, `env` (keys must match `EVAL_[A-Z0-9_]*`) ([evals#prompt-md-fields](https://code.claude.com/docs/en/plugin-evals#prompt-md-fields)). Each `graders/<name>.md` has `type`, `weight` (default 1), an optional `arm`, and the type's options in its frontmatter; for an `llm` grader the body is the rubric ([evals#grader-frontmatter](https://code.claude.com/docs/en/plugin-evals#grader-frontmatter)). Locally, `init --bare` wrote `max_turns: 10`, `allowed_tools: [Read, Glob, Grep, Skill]` and one `type: llm`, `weight: 1` grader.
- **`case.yaml`.** It requires `schema_version: "1.1"` and `name`. `description`, `tags`, `plugins`, `runs` and `expected_outcome` go at the top level. `model`, `max_turns`, `timeout_seconds`, `allowed_tools`, `append_system_prompt`, `env` and `prompt` go under `execution:`. `graders:` is a list of entries, each a `name` plus the grader's keys, with the `llm` rubric in `criteria`. Three fields exist only here: `context.scaffold_script`, `context.history_file` (a `.jsonl` transcript to resume) and `context.add_dirs` (read-only fixture directories). When both files exist, the `prompt.md` frontmatter wins, its body is the prompt, and `graders/*.md` are added after the graders in `case.yaml` ([evals#case-yaml-fields](https://code.claude.com/docs/en/plugin-evals#case-yaml-fields)).
- **Grader types.** There are six, and "There are no custom-code graders". `regex`, `tool_used`, `tool_order` and `file_exists` are free; `llm` and `baseline` call a judge model ([evals#grade-the-result](https://code.claude.com/docs/en/plugin-evals#grade-the-result), [evals#grader-types](https://code.claude.com/docs/en/plugin-evals#grader-types)):
  - `regex`: `pattern` (JavaScript syntax, so use `flags: i`, not `(?i)`), `match: not_contains` or `"count:N"`, and `target`.
  - `tool_used`: `tool`, `input_match` (regex over the JSON-encoded input), `min` (default 1) and `max` (default unlimited). `min: 0` with `max: 0` asserts the tool was never called.
  - `tool_order`: `before` and `after`, each a tool name or `{tool, input_match}`.
  - `file_exists`: `path` (a glob) and `exists`. It only sees files created during the run.
  - `llm`: `criteria` and `focus`. It passes when the judge votes PASS in at least 2 of 3; the judge is Haiku (per the CLI help) unless you set `--judge-model`.
  - `baseline`: `baseline_file` (a reference `.jsonl` transcript) and `criteria`.
- **What a grader reads.** `target` (regex) and `focus` (llm) accept `last_message` (the default), `trace` (JSON lines, so quotes appear as `\"`), `files` (paths created during the run, not contents), `{ source: file, path: <p> }` (one file's contents; PNG, JPEG, GIF and WebP go to the judge as images, other binaries are refused) and `mock_calls` ([evals#what-a-grader-can-look-at](https://code.claude.com/docs/en/plugin-evals#what-a-grader-can-look-at)). To check a script or build result, have the prompt ask Claude to run it and write the outcome to a file, `regex`-grade that file, and add a `tool_used` grader on `Bash` whose `input_match` names the command ([evals#grade-the-result](https://code.claude.com/docs/en/plugin-evals#grade-the-result)).
- **Asserting that a skill fires.** Use `type: tool_used`, `tool: Skill`, `input_match: '"skill"\s*:\s*"(?:[\w-]+:)?<skill-name>"'`. It passes if Claude invoked the skill at least once, by its bare or its `plugin:skill` name ([evals#write-a-case-manually](https://code.claude.com/docs/en/plugin-evals#write-a-case-manually)). List `Skill` in `allowed_tools`, as the docs' example and the template do. To assert the skill must *not* fire, use the same grader with `min: 0`, `max: 0` and `arm: both`.
- **With/without-plugin ablation.** `--ablation with-without` is the default whenever a plugin resolves, and the summary shows `WITH`, `W/OUT` and `Δ`. In a two-arm run, every `tool_used: Skill` grader and every `arm: with-only` grader is left out of both arms' scores and shown as a "plugin-fired indicator", unless every grader in the case is of that kind. `--ablation none` runs one arm, excludes nothing, and halves the cost ([evals#compare-against-a-no-plugin-baseline](https://code.claude.com/docs/en/plugin-evals#compare-against-a-no-plugin-baseline)).
- **Runs and thresholds.** A run's score is the weighted fraction of graders that passed; a case's score is the mean over its runs. A case passes when its with-plugin score is at least `--threshold`, which defaults to **1.0**, so any case short of perfect exits 1 ([evals#how-a-case-is-scored](https://code.claude.com/docs/en/plugin-evals#how-a-case-is-scored)). `--runs` overrides a case's `runs`, `-j` sets concurrency from 1 to 8, and `--max-cost-usd` sets a cost ceiling ([evals#command-options](https://code.claude.com/docs/en/plugin-evals#command-options)). Exit codes: 0 all cases passed; 1 below threshold, a load error, no cases, or an untrusted directory; 2 partial run; 130 interrupted; 143 terminated ([evals#run-evals-in-ci](https://code.claude.com/docs/en/plugin-evals#run-evals-in-ci)).
- **`scaffold_script`.** A Bash script in the case directory that runs in the empty workspace before Claude starts, to create fixtures or a git repository. It runs as you, outside the agent's sandbox, and **only with `--scaffold`**; `--no-scaffold` forces it off ([evals#add-setup-or-history-with-case-yaml](https://code.claude.com/docs/en/plugin-evals#add-setup-or-history-with-case-yaml)). The docs say nothing about native Windows; the CLI help says only that it "runs author-supplied bash as you".
- **`experimental.evals`.** A `plugin.json` key taking a string or array: a relative path of plain directory names below the plugin root, such as `"quality/evals"`, used instead of `evals/`. `--eval-dir` overrides it. An absolute path or one containing `..` is rejected; an unusable manifest value prints a warning and the run falls back to `evals/` ([plugins-reference#component-path-forms](https://code.claude.com/docs/en/plugins-reference#component-path-forms), [evals#use-a-different-eval-directory](https://code.claude.com/docs/en/plugin-evals#use-a-different-eval-directory)).
- **Isolation.** Each run starts in an empty workspace with no user settings, CLAUDE.md files, other plugins or personal skills, and the Artifact tool off ([evals#how-runs-are-isolated](https://code.claude.com/docs/en/plugin-evals#how-runs-are-isolated)). A run can use only the read-only tools its case lists (from Read, Glob, Grep, NotebookRead, Skill, Agent, TodoWrite and the Task tools) plus what `--allow-tools` grants, such as `"Bash(python *)"`. Granting Bash or PowerShell requires an OS sandbox, and **native Windows has none, so suites that run scripts must run under WSL2** ([evals#grant-tools](https://code.claude.com/docs/en/plugin-evals#grant-tools)).
- **CI.** `claude plugin eval . --trust-plugin --json results.json --threshold 0.8 --model <pinned> --judge-model <pinned> --no-publish --max-cost-usd 20`. The JSON has `schemaVersion: 1` with `aggregates.overallScore`, `aggregates.meanDelta`, `cases[].aggregates.delta` and `partial` ([evals#json-result](https://code.claude.com/docs/en/plugin-evals#json-result)).

**Minimal example case**, in the single-file form, saved as `evals/axe-pass-not-compliance/case.yaml`:

```yaml
schema_version: "1.1"
name: axe-pass-not-compliance
runs: 3
execution:
  prompt: "Our marketing site passes axe with zero violations. Can I tell procurement we're WCAG 2.2 AA compliant?"
  max_turns: 10
  allowed_tools: [Read, Glob, Grep, Skill]
graders:
  - name: skill-fired          # shown as a plugin-fired indicator in a two-arm run
    type: tool_used
    tool: Skill
    input_match: '"skill"\s*:\s*"(?:[\w-]+:)?a11y-audit-runner"'
  - name: verdict
    type: llm
    criteria: |
      PASS if the reply says a clean axe run does not by itself establish WCAG 2.2 AA conformance and names at least one manual check (keyboard, screen reader, zoom/reflow).
      FAIL if it confirms compliance on the strength of the axe result.
```

In the `prompt.md` form of the same case, the prompt is the body of `prompt.md`, with `runs`, `max_turns` and `allowed_tools` in its frontmatter. Each grader becomes a file: `graders/skill-fired.md` (frontmatter only) and `graders/verdict.md` (`type: llm`, rubric as the body). To iterate cheaply, run `claude plugin eval . --case axe-pass-not-compliance --runs 1 --ablation none`.

## 2. Plugin components available today

Components live at the plugin root; only `plugin.json` goes inside `.claude-plugin/` ([plugins-reference#standard-layout](https://code.claude.com/docs/en/plugins-reference#standard-layout)).

- **Skills.** `skills/<name>/SKILL.md` is invoked as `/plugin:name`. Directories in the manifest's `skills` field *add to* the default scan ([plugins-reference#how-each-key-combines-with-its-default-location](https://code.claude.com/docs/en/plugins-reference#how-each-key-combines-with-its-default-location)).
- **Commands are now skills.** "Custom commands have been merged into skills." Flat `commands/*.md` files still load as skills, but that layout is legacy ("Use `skills/` for new plugins"). Command files accept the same frontmatter except `name` and `paths` ([skills](https://code.claude.com/docs/en/skills), [skills#where-skills-live](https://code.claude.com/docs/en/skills#where-skills-live)).
- **Agents.** Files go in `agents/*.md`, and a subfolder becomes part of the scoped name (`plugin:sub:name`). Required frontmatter: `name`, `description`. Optional: `tools`, `disallowedTools`, `model` (`sonnet`, `opus`, `haiku`, `fable`, a model ID, or `inherit`), `effort`, `maxTurns`, `skills` (preloads each skill's **full** content), `memory` (`user`, `project` or `local`), `background`, `omitClaudeMd`, `isolation: worktree`, `color`, `experimental.cacheTtl`. Plugin agents ignore `hooks`, `mcpServers` and `permissionMode` for security, and don't support `initialPrompt`. Re-read 2026-10-09 (§8): a skill with `disable-model-invocation: true` cannot be preloaded, `${CLAUDE_PLUGIN_ROOT}` is substituted in agent bodies, and an unknown field is ignored without an error ([plugins-reference#agents](https://code.claude.com/docs/en/plugins-reference#agents), [sub-agents#supported-frontmatter-fields](https://code.claude.com/docs/en/sub-agents#supported-frontmatter-fields)).
- **Hooks.** `hooks/hooks.json` (optional top-level `description`) or inline in `plugin.json`. They merge with the user's and the project's hooks ([plugins-reference#hooks](https://code.claude.com/docs/en/plugins-reference#hooks), [hooks#reference-scripts-by-path](https://code.claude.com/docs/en/hooks#reference-scripts-by-path)).
- **MCP servers.** `.mcp.json` or inline `mcpServers`. They start automatically when the plugin is enabled, and their tools are named `mcp__plugin_<plugin>_<server>__<tool>`. `${CLAUDE_PLUGIN_ROOT}` resolves in `command`, `args` and `env` ([plugins-reference#mcpservers](https://code.claude.com/docs/en/plugins-reference#mcpservers), [plugins-reference#environment-variables](https://code.claude.com/docs/en/plugins-reference#environment-variables)).
- **LSP servers.** `.lsp.json` requires `command` (the binary must be on PATH, installed separately) and `extensionToLanguage`. Optional: `args`, `env`, `initializationOptions`, `settings`, `workspaceFolder`, `startupTimeout`, `shutdownTimeout`, `restartOnCrash`, `maxRestarts`, `diagnostics` ([plugins-reference#lspservers](https://code.claude.com/docs/en/plugins-reference#lspservers)).
- **Output styles.** `output-styles/*.md` with frontmatter `name`, `description` and `keep-coding-instructions`. A plugin style can set `force-for-plugin: true` to apply automatically, overriding the user's `outputStyle` ([output-styles#frontmatter](https://code.claude.com/docs/en/output-styles#frontmatter)).
- **Other components.** `bin/` is added to the Bash tool's PATH while the plugin is enabled. There is also `workflows/`, a `settings.json` that supports only `agent` and `subagentStatusLine`, and the manifest keys `dependencies` and `channels`. `themes/` and `monitors/monitors.json` are experimental; a monitor is a background command whose stdout lines reach Claude as notifications, `when: "on-skill-invoke:<skill>"` starts it with a skill, and monitors run in interactive CLI sessions only. A plugin-root `CLAUDE.md` is **not** loaded ([plugins-reference#standard-layout](https://code.claude.com/docs/en/plugins-reference#standard-layout), [plugins-reference#monitors](https://code.claude.com/docs/en/plugins-reference#monitors), [plugins-reference#standard-layout](https://code.claude.com/docs/en/plugins-reference#standard-layout)).

**Hooks in detail**
- **Handler format.** `{"hooks":{"PostToolUse":[{"matcher":"Write|Edit","hooks":[{"type":"command","command":"node","args":["${CLAUDE_PLUGIN_ROOT}/scripts/check.js"]}]}]}}`. Handler types are `command`, `http`, `mcp_tool`, `prompt` and `agent`. Common fields: `if` (one permission rule such as `"Edit(**/*.css)"`, tool events only), `timeout` (600 s for command hooks), `statusMessage`, and `once` (honoured only in skill frontmatter). Command hooks add `args` (exec form), `async`, `asyncRewake` and `shell` ([hooks#common-fields](https://code.claude.com/docs/en/hooks#common-fields), [hooks#command-hook-fields](https://code.claude.com/docs/en/hooks#command-hook-fields)).
- **Events.** 33 in total, including SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch, Stop, SubagentStart/SubagentStop, PreCompact and FileChanged ([plugins-reference#hooks](https://code.claude.com/docs/en/plugins-reference#hooks)).
- **Matchers.** `*`, empty or omitted matches everything. A matcher made only of letters, digits, `_`, `-`, spaces, `,` and `|` is an exact name or list of names. Anything else is an unanchored JavaScript regex; write `^Edit$` to anchor it ([hooks#matcher-patterns](https://code.claude.com/docs/en/hooks#matcher-patterns)).
- **Paths on Windows.** `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` and `${CLAUDE_PROJECT_DIR}` are substituted and also exported as environment variables. Prefer exec form (`args`). Shell form runs through Git Bash on Windows, or PowerShell without Git Bash. Exec form on Windows needs a real `.exe`, so run `node` or `python` with the script path; `.cmd` shims won't spawn ([hooks#exec-form-and-shell-form](https://code.claude.com/docs/en/hooks#exec-form-and-shell-form)).
- **Exit codes.** **0** is success. Stdout that starts with `{` and ends with `}` is parsed as JSON; plain stdout reaches Claude only on UserPromptSubmit, UserPromptExpansion, SessionStart and PostModelSwitch, and otherwise goes to the debug log. Claude never sees stderr on exit 0. **2** is a blocking error on events that can block: PreToolUse blocks the call, UserPromptSubmit erases the prompt, Stop keeps Claude working. On PostToolUse, exit 2 "Shows stderr to Claude; the tool already ran". **Any other code, including 1,** never blocks on its own: the action proceeds and the transcript shows a "hook error" notice ([hooks#exit-code-output](https://code.claude.com/docs/en/hooks#exit-code-output), [hooks#exit-code-2-behavior-per-event](https://code.claude.com/docs/en/hooks#exit-code-2-behavior-per-event)).
- **How output reaches Claude.** `hookSpecificOutput.additionalContext` becomes a system reminder placed next to the tool result (PostToolUse) or the prompt (UserPromptSubmit). On PostToolUse, `decision: "block"` with a `reason` adds that reason beside the result, and `updatedToolOutput` replaces the result. `continue: false` stops Claude, and `systemMessage` warns the user. Each string is capped at 10,000 characters. `async: true` runs a hook in the background, and `asyncRewake` also wakes Claude on exit 2 ([hooks#json-output](https://code.claude.com/docs/en/hooks#json-output), [hooks#add-context-for-claude](https://code.claude.com/docs/en/hooks#add-context-for-claude), [hooks#posttooluse-decision-control](https://code.claude.com/docs/en/hooks#posttooluse-decision-control)).

**`userConfig`**
- **Declaring options.** Declare them in `plugin.json`, e.g. `"userConfig":{"site_url":{"type":"string","title":"Site URL","description":"…"}}`. `type` is `string`, `number`, `boolean`, `directory` or `file`. Optional fields: `sensitive`, `required`, `default`, `options`, `multiple`, `min`/`max`. `options` (a pick list) needs v2.1.271 or later, and older versions can't load the plugin. Users are prompted at enable time and can edit values in `/config` (v2.1.269+) or set them with `claude plugin install --config key=value` ([plugins-reference#user-configuration](https://code.claude.com/docs/en/plugins-reference#user-configuration), [plugins-reference#plugin-install](https://code.claude.com/docs/en/plugins-reference#plugin-install)).
- **Reading option values.** `${user_config.KEY}` is substituted in MCP and LSP configs, in exec-form hook commands, and (non-sensitive values only) in skill and agent content. Shell-form hooks, monitor commands and `headersHelper` reject it. Hook processes receive every value as `CLAUDE_PLUGIN_OPTION_<KEY>`. Values are stored in the user's `settings.json` under `pluginConfigs[<id>].options`; sensitive values go to the keychain or credentials file, and project settings are ignored ([plugins-reference#user-configuration](https://code.claude.com/docs/en/plugins-reference#user-configuration)).
- **Scripts run through the Bash tool.** `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` aren't in the Bash tool's environment, and the `CLAUDE_PLUGIN_OPTION_*` variables are documented for hook processes only. Pass values as arguments written into the skill text instead ([plugins-reference#environment-variables](https://code.claude.com/docs/en/plugins-reference#environment-variables)).

## 3. Skill frontmatter and substitutions

- **Fields.** All optional; unknown fields are ignored without an error ([skills#frontmatter-reference](https://code.claude.com/docs/en/skills#frontmatter-reference)):
  - `name`: in a plugin skill, the last segment of `/plugin:name`; defaults to the directory name.
  - `description`: recommended; falls back to the body's first non-empty line. `when_to_use` is appended to it in the listing.
  - `argument-hint`; `arguments` (named `$name` arguments); `disable-model-invocation`; `user-invocable`.
  - `allowed-tools` pre-approves tools for the invoking turn only and doesn't restrict any tool. Also `disallowed-tools`, `model` (for the current turn) and `effort`.
  - `context: fork`, with `agent` and `background`. `hooks`, registered when the skill is invoked and kept for the session.
  - `paths` (globs limiting auto-load), `shell` (`bash` or `powershell`, for injected commands), `metadata`, `license`, `compatibility` (max 500 chars).
  - If the YAML doesn't parse, the skill loads with no metadata, so Claude can't match its description ([skills#skill-not-triggering](https://code.claude.com/docs/en/skills#skill-not-triggering)).
- **Description length.** The skill listing truncates the combined `description` and `when_to_use` at **1,536 characters** (setting `skillListingMaxDescChars`) ([settings-reference#skilllistingmaxdescchars](https://code.claude.com/docs/en/settings-reference#skilllistingmaxdescchars)). The Agent Skills spec caps `description` at 1,024 characters and `name` at 64 (lowercase, digits, hyphens; must match the folder) ([agentskills.io/specification](https://agentskills.io/specification)). claude.ai uploads, the Skills API and `package_skill.py` enforce the spec and reject non-spec keys such as `argument-hint` ([skills#using-skill-frontmatter-outside-claude-code](https://code.claude.com/docs/en/skills#using-skill-frontmatter-outside-claude-code)).
- **Who can invoke a skill.** By default the description is always in context and both the user and Claude can invoke the skill. `disable-model-invocation: true` keeps the description out of context, so only the user can invoke the skill and it can't be preloaded into subagents. `user-invocable: false` hides the skill from the `/` menu, but Claude can still invoke it ([skills#control-who-invokes-a-skill](https://code.claude.com/docs/en/skills#control-who-invokes-a-skill)).
- **Substitution: yes, both.** `${CLAUDE_SKILL_DIR}` (the skill's own folder, not the plugin root) and `${CLAUDE_PROJECT_DIR}` are substituted in SKILL.md text and in Bash rules in `allowed-tools`. In plugin skills only, so are `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}`. Also available: `$ARGUMENTS`, `$N`, `$name`, `${CLAUDE_SESSION_ID}`, `${CLAUDE_EFFORT}`. The documented pattern pairs `allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)` with a body that runs that exact path, so the script runs with no permission prompt ([skills#available-string-substitutions](https://code.claude.com/docs/en/skills#available-string-substitutions)).
- **Injected commands (`` !`cmd` ``).** Any non-zero exit aborts the whole invocation. They never prompt: outside auto mode, a command that isn't already allowed by permission rules or the skill's `allowed-tools` aborts the invocation. `shell: bash` fails on Windows without Git Bash ([skills#how-injected-commands-run](https://code.claude.com/docs/en/skills#how-injected-commands-run)).
- **Size.** An invoked skill stays in context. After compaction, each is re-attached with only its first 5,000 tokens, within 25,000 tokens in total ([skills#skill-content-lifecycle](https://code.claude.com/docs/en/skills#skill-content-lifecycle)). The spec recommends SKILL.md stay under 5,000 tokens and 500 lines, with detail in reference files ([agentskills.io/specification](https://agentskills.io/specification)).

## 4. The skill listing budget

- **What is listed.** Every turn, Claude receives a listing of skill names and descriptions, and **every name is always listed**. Over budget, descriptions are dropped **starting with the skills the user invokes least**. Those skills stay invocable, but Claude is "less likely to choose one on its own" ([skills#skill-descriptions-are-cut-short](https://code.claude.com/docs/en/skills#skill-descriptions-are-cut-short), [settings-reference#skilllistingbudgetfraction](https://code.claude.com/docs/en/settings-reference#skilllistingbudgetfraction)).
- **Budget size.** 1% of the context window, set by `skillListingBudgetFraction` (default `0.01`, range above 0 up to 1), with an 8,000-character fallback. `SLASH_COMMAND_TOOL_CHAR_BUDGET` sets a fixed character count; its name is legacy ([env-vars](https://code.claude.com/docs/en/env-vars)).
- **User-side controls.** `skillOverrides` takes `on`, `name-only`, `user-invocable-only` or `off`, but "Plugin skills are not affected by `skillOverrides`" ([skills#override-skill-visibility-from-settings](https://code.claude.com/docs/en/skills#override-skill-visibility-from-settings)). To diagnose: `/doctor` shows the listing's cost and biggest contributors, the Skills row in `/context` shows its size after the budget, `--debug` logs an over-budget warning, and `/skill-doctor` (v2.1.252+) shows each skill's cost and use ([skills#find-unused-skills](https://code.claude.com/docs/en/skills#find-unused-skills)).
- **Documented levers for plugin authors.** Put the key use case first and trim `description` and `when_to_use`. Mark user-only workflows `disable-model-invocation: true`, which takes them out of the listing. Re-run `tool_used: Skill` evals after each description change ([skills#skill-descriptions-are-cut-short](https://code.claude.com/docs/en/skills#skill-descriptions-are-cut-short), [skills#control-who-invokes-a-skill](https://code.claude.com/docs/en/skills#control-who-invokes-a-skill), [skills#skill-not-triggering](https://code.claude.com/docs/en/skills#skill-not-triggering)).
- **What evals can't show here.** Eval runs load only your plugin, so they measure triggering *without* competition from a crowded listing ([evals#how-runs-are-isolated](https://code.claude.com/docs/en/plugin-evals#how-runs-are-isolated)).

## Implications for web-design-suite *(inference)*

- **What I observed.** In the session that produced this report, the listing held about 730 skills. Only about 14, all bundled or host skills, had descriptions; all 13 `web-design-suite:*` entries were **name-only**.
- **Why it happens.** The plugin's 13 descriptions add up to about 11,800 characters (780–961 each), more than the whole 8,000-character fallback budget on their own. In a crowded install they will usually lose their descriptions.
- **Names carry the signal.** Names always survive, so make them self-explanatory, and front-load a first sentence that works on its own.
- **Routing that ignores the budget.** Two options don't depend on the listing at all. One is a plugin `UserPromptSubmit` hook that matches keywords (WCAG, axe, Figma variables, etc.) and returns `additionalContext` naming the right skill. The other is a plugin agent that preloads skills through `skills:`.
- **Evals for this plugin.** Give each case a skill-specific `input_match`, so mis-routing between sibling skills shows up. Evals that run the validator scripts need `--allow-tools "Bash(...)"`, and therefore WSL2 on this machine; trigger-only suites using `Read, Glob, Grep, Skill` run natively.

## 6. Re-checked on 2026-10-08 (before P25)

Re-read: the hooks page ([hooks](https://code.claude.com/docs/en/hooks)), the mods overview and the mods reference ([mods overview](https://code.claude.com/docs/en/plugins/mods/overview), [mods reference](https://code.claude.com/docs/en/plugins/mods/reference)). §2's hook facts still hold. These are new or sharper:

- **Timeouts.** "Defaults: 600 for `command`, `http`, and `mcp_tool`; 30 for `prompt`; 60 for `agent`." They drop to 30 seconds on `UserPromptSubmit`, `PreModelSwitch` and `PostModelSwitch`, and to 10 on `MessageDisplay` ([hooks#common-fields](https://code.claude.com/docs/en/hooks#common-fields)).
- **PreToolUse.** `permissionDecision` takes `allow`, `deny`, `ask` or `defer`; for `deny`, the `permissionDecisionReason` is shown to Claude, and exit 2 routes the same way. For the file tools, "`tool_input.file_path` is always absolute", with backslashes on Windows. The tool list names Write and Edit, and no longer MultiEdit.
- **PostToolUse and PostToolBatch.** PostToolUse's `decision: "block"` "adds the `reason` next to the tool result"; `additionalContext` goes beside it, and `updatedToolOutput` replaces what Claude sees. PostToolBatch fires "exactly once with the full batch", with a `tool_calls` array, and its `additionalContext` is injected once before the next model call.
- **UserPromptSubmit.** The text is in `prompt`; pasted content may arrive wrapped in `<pasted_content>` lines. Plain stdout or `additionalContext` adds context; `decision: "block"` stops the prompt.
- **The 10,000-character cap.** Over it, Claude Code saves the output to a file and shows "a preview of up to the first 2,000 characters".
- **Exit 1** without valid JSON is a non-blocking error: "If your hook is meant to enforce a policy, use `exit 2`."
- **Mods** run "in the Claude Code CLI and in the Code tab of the Claude Desktop app", from v2.1.287 in the terminal and v2.1.286 in the Desktop app. Their hooks run in `claude -p` and the Agent SDK, but not in a WSL session of the Desktop app, "because plugins aren't available in WSL sessions". A mod's `hooks/hooks.json` holds `modules`, and may also hold settings hooks under `hooks`. A hook's own time is capped at 10 seconds, apart from mods API calls; `$.process.run` defaults to 30 seconds, and runs for 10 minutes at most. `disableAllHooks` stops installed mods as it stops command hooks. The overview's comparison: a settings hook is the pick "when you want to block, allow, or log an event with a script you already have", and a mod is the pick for a pane, a band, a custom command, or to rewrite an event.

**P25's choice: command hooks, run by node.** *(decision, 2026-10-08)*
- **A command hook.** The gate, the guard and the router block, allow or add context with scripts the plugin already has, which is the case the comparison gives command hooks. They run on every version that loads plugin hooks, not only 2.1.287 or later, and the suite tests them as Claude Code runs them: JSON on stdin, JSON out.
- **Run by node.** Exec form on Windows needs a real executable. Python has no name that works on every system: `python3` is the Store's placeholder on Windows, and macOS has no `python`. `node` has one name everywhere. The Node hook reads the config through `project_config.mjs` and calls Python only for the gate, in an opted-in project, after it has found a Python 3.
- **A mod later.** A mod remains the way to draw: a findings pane, or a band above the prompt. The plugin can add one beside the command hooks, in the same `hooks/hooks.json`, once 2.1.287 is old enough to require.

## 9. Re-checked on 2026-10-10 (before P28)

Re-read: the MCP page's plugin servers, output limits and backgrounding ([mcp#plugin-provided-mcp-servers](https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers), [mcp#mcp-output-limits-and-warnings](https://code.claude.com/docs/en/mcp#mcp-output-limits-and-warnings), [mcp#automatic-backgrounding-of-long-tool-calls](https://code.claude.com/docs/en/mcp#automatic-backgrounding-of-long-tool-calls)) and the manifest reference's `mcpServers`, `lspServers`, environment variables and standard layout ([plugins-reference#mcpservers](https://code.claude.com/docs/en/plugins-reference#mcpservers), [#lspservers](https://code.claude.com/docs/en/plugins-reference#lspservers), [#where-each-variable-resolves](https://code.claude.com/docs/en/plugins-reference#where-each-variable-resolves), [#standard-layout](https://code.claude.com/docs/en/plugins-reference#standard-layout)). §2's MCP and LSP bullets still hold. These are new or sharper:

- **Declaring a server.** "Plugins define MCP servers in `.mcp.json` at the plugin root or inline in `plugin.json`". "At session startup, Claude Code connects the servers for enabled plugins automatically." The manifest's `mcpServers` "Merges": ".mcp.json at the plugin root first, then each declared shape in order. A server name declared later replaces an earlier one."
- **Variables.** For a stdio server, `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` and `${CLAUDE_PROJECT_DIR}` resolve in "`command`, `args`, `env`", and the process receives `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA`. The page's stdio section says Claude Code sets `CLAUDE_PROJECT_DIR` in a spawned server's environment.
- **Names.** "The full form is `mcp__plugin_<plugin-name>_<server-name>__<tool-name>`". "Use this full name when referencing the tool in permission rules, a skill's `allowed-tools` list, a subagent's `tools` field, or a hook matcher." The server registers as `plugin:<plugin-name>:<server-name>`.
- **Output.** "Claude Code displays a warning when any MCP tool output exceeds 10,000 tokens"; "the default maximum is 25,000 tokens" (`MAX_MCP_OUTPUT_TOKENS`). A tool can raise its own cap with `_meta` `"anthropic/maxResultSizeChars"`.
- **Long calls.** "An MCP tool call in the main conversation that is still running after two minutes moves to a background task", from v2.1.212; not for subagents' calls, nor in non-interactive mode. A stdio call's idle window is 30 minutes.
- **Validation.** `claude plugin validate` checks each MCP entry from v2.1.281: "an entry Claude Code would drop when it loads the plugin, a `${user_config.KEY}` reference to an option the manifest doesn't declare, and a remote `url` that isn't a valid absolute URL" are errors. Observed with 2.1.293: run on the plugin folder, it validates the `marketplace.json` beside `plugin.json`; run on `plugin.json`, it reads `.mcp.json` (an undeclared `${user_config.nope}` fails it).
- **LSP.** "Each server config is a strict object … An unknown key fails validation." `command` is required, "Language server binary. No spaces unless the value starts with `/`; put arguments in `args`", with `extensionToLanguage`; `${...}` resolves in "`command`, `args`, `env`, `workspaceFolder`". `transport` accepts `socket` "but runs every server over stdio". `diagnostics` "Whether to push diagnostics into context after edits. Defaults to `true`". So `command: "node"` with the server script in `args` needs no binary on PATH beyond node, which the hooks already need.
- **`bin/`.** "Files here are on the Bash tool's `PATH` while the plugin is enabled, so Claude runs them as bare commands. claude.ai and Cowork don't install a plugin that has this directory, including one you distribute through claude.ai organization settings."

**P28's choice: the MCP server runs under node.** *(decision, 2026-10-10)* The plan said a Python server, but `command` needs a real executable, and Python has no name that works on every system (§6). `node mcp/design_gates.mjs` speaks MCP over stdio with Node's standard library, finds Python as the hooks do, and runs the skills' scripts. Observed with 2.1.293 on Windows: `claude --plugin-dir plugins/web-design-suite mcp list` reports `plugin:web-design-suite:gates: node …/mcp/design_gates.mjs - ✔ Connected`.

**P28's LSP spike: not shipped.** *(decision, 2026-10-10)* The components page ([plugins/components#lsp-servers](https://code.claude.com/docs/en/plugins/components#lsp-servers)) settles it before any code: "each file extension gets one server", and "when two enabled servers claim the same extension, the first registered handles those files and the other isn't used for them, whether the servers come from one plugin or two". An LSP for the audit would claim `.css`, `.html`, `.js`, `.jsx`, `.ts` and `.tsx` in every project, opted in or not:
- where it registered first, it would take type errors and code navigation away from a user of Anthropic's `typescript-lsp`, and pre-empt any CSS or HTML server they add later;
- where it registered second, it would never run.

What it would have added, the audit's findings after each edit, the opt-in `designGate` hook already gives (P25), and hooks also run in `claude -p`, which the evals use, while "Code intelligence plugins work in terminal sessions". Two more facts from the page: `claude plugin validate` "doesn't read" `.lsp.json` (an invalid entry skips the whole file at load), and a server's stdout must carry protocol messages only. The way back, if Claude Code ever lets servers share an extension: a node server in `lsp/`, `"command": "node"`, silent unless the project's `hooks.designGate` is on.
