## A. Issues

**SB-A1 · high · stack-vanilla-css.md:364-487 (`box-shadow` at :396), stack-css-modules.md:460-563 (:492)** — The canonical Button shows no focus ring when reached by keyboard. `.button { box-shadow: var(--btn-shadow) }` sits in `@layer components`. That beats reset.css:334-348 `:focus-visible { box-shadow: var(--shadow-focus); outline: … transparent }`, which sits in `@layer reset`. The button declares no `:focus-visible` rule of its own. *Evidence:* I loaded the starter reset/tokens/base/layout plus §8's CSS in Chromium, then pressed Tab. The link got the ring. The default button showed `:focus-visible`=true, computed `box-shadow: none`, `outline-color: rgba(0,0,0,0)`. The primary button's box-shadow was only its card shadow. This fails WCAG 2.4.7 in the "reference implementation". *Fix:* give every component that sets `box-shadow` a `&:where(:focus-visible){ box-shadow: var(--elevation-focus), var(--btn-shadow) }` block. Better: make the reset ring an `outline`, which no component box-shadow can override. Confidence high.

**SB-A2 · high · theme.css:738-741, tailwind.config.ts:588-591, stack-tailwind.md:1221 (used at :653)** — `@utility focus-ring { outline: none; box-shadow: var(--shadow-focus) }` takes away the forced-colors fallback. The utilities layer beats the reset's transparent outline. In the browser the focused button had computed `outline-style: none`. Forced-colors mode discards `box-shadow`, so the focus indicator disappears entirely. That breaks the token-contract "Accessibility floor" (token-contract.md:109) and accessibility.md §3. It also reads Tier-1 `--shadow-focus`, although tokens.css:349-354 added `--elevation-focus` for exactly this case. For comparison, Tailwind's own `outline-hidden` emits `@media (forced-colors: active){ outline: 2px solid transparent }` (seen in the probe). *Fix:* `outline: var(--stroke-focus) solid transparent; outline-offset: var(--stroke-focus); box-shadow: var(--elevation-focus)`. (SS-A6 found the same pattern in pattern-invention.md.) Confidence high.

**SB-A3 · high · audit_design.py:418-423, 612, 644, 659, 667, 688, 695** — Any `var(` anywhere in a value turns off every L1 check for that declaration. `value_is_tokenized` returns True as soon as the string contains `"var(--"`, and the colour, shadow, type, radius and motion checks are all guarded by `"var(--" not in value`. *Repro:* `fx/src/components/var-mixed.css` has 11 violations, including `padding: var(--pad-block-sm) 13px`, `transition: opacity 300ms var(--ease-out)`, `font: 600 14px/1.2 var(--font-sans)`, `box-shadow: 0 1px 2px #000, var(--elevation-card)`, `color-mix(…, #ff0000)`, `margin: var(--gap-grouped) auto` (in a component) and `var(--fg-muted, #666)`. Stylelint does not constrain the `transition` or `animation` shorthands either, so neither gate catches it. *Fix:* strip each `var(…)`, including its fallback, and test what remains. Add shorthand allowlists to stylelint. Confidence high.

## B. Gaps

- **SB-B1 · templates aren't audited.** audit_design skips `.html/.vue/.svelte/.astro`, and ESLint `files` is `**/*.{js,jsx,ts,tsx}`. `site/index.html` with `style="margin-top:8px;color:#ff0000;z-index:9999"` and a `<style>` block, plus `Card.vue`, came back "clean — all nine laws hold". The vanilla stack, called the reference implementation, writes most of its markup in HTML (stack-vanilla-css.md:630-634). Scope: feed `style=""` attributes and `<style>`/SFC blocks to `audit_css`, and class attributes to the Tailwind checks.
- **SB-B2 · no executable tests for the configs.** There are no ESLint or stylelint fixtures, no Tailwind compile test and no doc-snippet test. The scratch harnesses would have caught SB-A2, A5, A12, A13, A18 and A19.
- **SB-B3 · focus, forced-colors and density aren't checked by any gate in the build flow.** They are manual items in review-checklist 8.2 and 8.9. SB-A1 and SB-A2 ship in the canonical examples.
